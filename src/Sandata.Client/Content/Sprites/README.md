# Sandata weapon sprites

The first real textures in `Sandata.Client`. Everything else the client draws
is a single 1x1 white pixel stretched into rectangles and tinted by a theme
role, and these two files are built to sit alongside that rather than to
replace it.

| File | Size | Grip anchor | What it is |
| --- | --- | --- | --- |
| `weapon-rifle.png` | 32x14 | 10, 7 | An AK-pattern rifle seen from directly above |
| `weapon-pistol.png` | 16x10 | 4, 6 | A Glock-pattern pistol seen from directly above |

## Two things the renderer depends on

**They point along +X, muzzle to the right.** The renderer rotates them to the
operator's facing, and a sprite authored pointing any other way would be
rotated to the wrong heading.

**The grip anchor above is the pivot**, in sprite pixel space. It is the point
the rotation happens about, and it corresponds to the same grip anchor the
primitive weapon bar used before these sprites existed. Move it here without
moving it in `OperatorRenderer`, and the weapon will swing about a point
somewhere off in space.

## Why they carry no colour

Each pixel is greyscale plus alpha — no hue at all. The renderer draws them
tinted by a theme colour, so 255 is that colour at full strength and the
darker steps are shading in the same colour. That keeps a weapon obeying the
active theme exactly as every rectangle in the client already does, and it
means a new theme never needs a new sprite.

## Regenerating

They are generated by `tools/sandata-weapon-sprites/generate.py`, which is
committed beside them and is the authoritative description of every box in
each silhouette:

```
uv run --with pillow python tools/sandata-weapon-sprites/generate.py
```

That script is an authoring tool. It never runs during a build, a test, or the
canonical gate, and the PNG files are committed so that a checkout does not
need Python to run the game. Edit the script rather than the PNG — a hand-edit
to the image is lost the next time anybody runs it.
